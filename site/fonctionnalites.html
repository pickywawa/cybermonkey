Des tests qui tiennent dans la duréeTests that last

Un test mobile échoue pour mille raisons qui ne sont pas des bugs : une popup, une session expirée, un écran qui s’affiche une seconde trop tard, un sélecteur qui bouge. Cette page décrit ce que Cybermonkey fait pour que un échec veuille dire quelque chose, et pour vous donner de quoi comprendre vite quand c’en est un.A mobile test fails for a thousand reasons that are not bugs: a popup, an expired session, a screen that shows up a second late, a selector that moved. This page describes what Cybermonkey does so that a failure means something, and gives you what you need to understand it quickly when it does.

Ce qu’un pas sait faireWhat a step can do

Chaque pas porte une variante par OS (Android et iOS) : un sélecteur, une opération, une valeur. Les opérations dépassent le simple appui :Each step carries a variant per OS (Android and iOS): a selector, an operation, a value. Operations go well beyond a tap:

Logique des scénariosScenario logic

  • Conditions (« Exécuter seulement si… ») : une vérification par OS contrôlée juste avant le pas. Non remplie, le pas et ses enfants sont ignorés sans échec : « si la bannière cookies est visible, la fermer ». Un délai court évite d’attendre un élément absent.Conditions (“Run only if…”): a per-OS check made right before the step. Not met, the step and its children are skipped without failing: “if the cookie banner is visible, close it”. A short timeout avoids waiting for a missing element.
  • Appel de sous-scénario : une action peut exécuter un autre scénario à sa place. « Se connecter » n’est écrit qu’une fois. Les boucles d’appels sont refusées et un scénario encore appelé ne peut pas être supprimé.Sub-scenario call: an action can run another scenario in its place. “Log in” is written once. Call loops are refused and a scenario still in use cannot be deleted.
  • Jeux de données : un scénario joué une fois par ligne d’un tableau (50 lignes max), chaque colonne devenant une variable ${COLONNE}. L’app est relancée entre deux lignes ; le rapport indique la ligne, et un pas en échec sur une seule ligne reste « échoué » dans la campagne.Datasets: a scenario played once per row of a table (50 rows max), each column becoming a ${COLUMN} variable. The app is relaunched between rows; the report shows the row, and a step that fails on a single row stays “failed” in the campaign.
  • Capture de valeur : lisez un numéro de commande ou un code à l’écran, gardez-le dans ${NOM} et utilisez-le dans les pas suivants (valeur, attendu, sélecteur).Value capture: read an order number or a code on screen, keep it in ${NAME} and use it in later steps (value, expectation, selector).

EnvironnementsEnvironments

Un projet peut porter plusieurs environnements (recette, préproduction, production…). Chacun a ses propres variables, qui remplacent les variables communes de même nom ; les autres restent héritées. Dans Variables, onglets « Communes » et un onglet par environnement ; dans la barre latérale, un sélecteur change l’environnement du projet.A project can hold several environments (staging, pre-production, production…). Each has its own variables, which override the common variables of the same name; the others stay inherited. In Variables, a “Common” tab plus one tab per environment; in the sidebar, a selector changes the project’s environment.

Le choix est global au projet : il s’applique à la création (l’IA voit les variables de l’environnement), à l’exécution, aux essais manuels et au serveur MCP (select_environment). Chaque rapport garde le nom de l’environnement utilisé. Les valeurs restent des variables du projet, pas un coffre-fort chiffré.The choice is project-wide: it applies to creation (the AI sees the environment’s variables), runs, manual tries and the MCP server (select_environment). Each report keeps the name of the environment used. Values remain project variables, not an encrypted vault.

Fiabilité : moins de faux échecsReliability: fewer false failures

  • Relance ciblée : un pas dont le composant est introuvable ou dont la vérification échoue est rejoué une fois (2e essai court). S’il passe, il est marqué instable au lieu d’être masqué. Jamais après une saisie, un défilement ou une erreur d’appareil : on ne duplique pas un effet.Targeted retry: a step whose component is not found or whose check fails is replayed once (short 2nd attempt). If it passes it is marked unstable instead of being hidden. Never after typing, scrolling or a device error: an effect is never duplicated.
  • Appui perdu : juste après un relancement l’app dessine encore son écran de lancement et un tap envoyé alors est perdu. Cybermonkey attend que l’app soit stable, et si une navigation ne se confirme pas alors que l’écran est resté inactif avec le composant toujours là, il répète l’appui une fois. Un spinner ou un bouton grisé = pas de second appui.Lost tap: right after a relaunch the app is still drawing its launch screen and a tap sent then is lost. Cybermonkey waits for the app to settle, and if a navigation is not confirmed while the screen stayed idle with the component still there, it repeats the tap once. A spinner or a disabled button = no second tap.
  • Historique de stabilité : pour chaque pas et OS, « passé 8 fois sur 10 » et un verdict — stable, instable, régression, premier échec, toujours en échec. Visible dans Progression et joint à chaque échec renvoyé par MCP : il distingue un bug d’un test fragile.Stability history: for each step and OS, “passed 8 times out of 10” and a verdict — stable, unstable, regression, first failure, always failing. Shown in Progress and attached to every failure returned by MCP: it tells a bug from a fragile test.
  • Sélecteurs durables : chaque sélecteur est classé — durable (identifiant technique), lié au texte affiché, fragile (XPath positionnel), par position. L’éditeur et la création IA avertissent ; l’outil MCP audit_selectors propose l’identifiant à demander aux développeurs et comment l’ajouter (accessibilityIdentifier, testTag, Semantics).Durable selectors: each selector is rated — durable (technical id), tied to displayed text, fragile (positional XPath), by position. The editor and AI creation warn; the MCP tool audit_selectors proposes the identifier to ask developers for and how to add it (accessibilityIdentifier, testTag, Semantics).
  • Réparations IA visibles : un bandeau « N sélecteurs réparés, tout appliquer » écrit les réparations dans les scénarios (l’ancien sélecteur devient un secours) ; sinon chaque run les répare à nouveau, plus lentement, et le changement de l’app reste caché. Outil MCP : apply_healed_selectors.Visible AI repairs: a “N selectors repaired, apply all” banner writes the repairs into the scenarios (the old selector becomes a fallback); otherwise every run repairs them again, more slowly, and the app change stays hidden. MCP tool: apply_healed_selectors.

Imprévus : popups, session expirée, plantageInterruptions: popups, expired session, crash

Une popup, un toast, un message « session expirée » ou un plantage peuvent survenir à n’importe quel moment, en création comme en exécution. Quand un pas échoue, Cybermonkey regarde si quelque chose s’est mis en travers avant de conclure à un échec, dans cet ordre :A popup, a toast, a “session expired” message or a crash can strike at any moment, in creation as in execution. When a step fails, Cybermonkey checks whether something got in the way before concluding it is a failure, in this order:

  1. L’app n’est plus au premier plan (plantage, fermeture) : elle est relancée, puis l’app revient à l’écran d’origine.The app is no longer in the foreground (crash, closed): it is relaunched, then brought back to the original screen.
  2. Une boîte de dialogue bloque l’écran (permission, alerte système ou de l’app) : les cas évidents sont traités par règle — permission accordée, suivi publicitaire refusé, bouton unique inoffensif — et l’IA tranche les cas flous. Un bouton qui supprime, déconnecte ou paie n’est jamais pressé.A dialog blocks the screen (permission, system or app alert): obvious cases are handled by rule — permission allowed, ad tracking declined, a single harmless button — and the AI settles the unclear ones. A button that deletes, logs out or pays is never pressed.
  3. Un de vos gestionnaires reconnaît l’écran : voir ci-dessous.One of your handlers recognises the screen: see below.
  4. En dernier recours, l’IA identifie l’intrus et ferme une popup inattendue avec le seul bouton sans effet métier (fermer, OK, plus tard). Si le seul bouton est risqué ou si elle hésite, elle ne touche à rien.As a last resort, the AI identifies the intruder and closes an unexpected popup with the one button that has no business effect (close, OK, later). If the only button is risky or it is unsure, it touches nothing.

Les gestionnaires d’imprévusInterruption handlers

Un gestionnaire est un scénario ordinaire à qui l’on dit « quand cet écran est affiché » (ses repères, comme n’importe quelle identité d’écran) et « ensuite ». Il n’entre dans aucune campagne : il se déclenche seul quand un pas échoue alors que son écran est présent, puis le pas est rejoué. Il se crée, s’édite, s’enregistre et se rejoue comme n’importe quel scénario, avec l’IA ou à la main, et peut appeler d’autres scénarios.A handler is an ordinary scenario to which you say “when this screen is showing” (its markers, like any screen identity) and “afterwards”. It is part of no campaign: it runs by itself when a step fails while its screen is present, then the step is replayed. It is created, edited, recorded and replayed like any scenario, with AI or by hand, and can call other scenarios.

Reprise : « rejouer le pas là où l’app se trouve », ou « revenir à l’écran d’origine puis rejouer » — l’écran d’où le pas est parti est retrouvé par le lien profond de l’écran, puis les navigations connues. Les gestionnaires s’enchaînent (jusqu’à 3 par échec).Resume: “replay the step where the app is”, or “go back to the original screen then replay” — the screen the step started from is found through the screen’s deep link, then the known navigations. Handlers chain (up to 3 per failure).

Exemple : reconnexion rapide. Un pas échoue parce qu’une popup « Session expirée » le recouvre. Gestionnaire 1 — écran : le texte de la popup ; pas : appuyer sur OK. L’appui déconnecte et ramène l’écran de connexion. Gestionnaire 2 — écran : l’écran de connexion ; pas : un appel au scénario « Se connecter » ; reprise : revenir à l’écran d’origine. Le moteur dit OK, se reconnecte, retourne là où il était, et rejoue le pas : passé, avec « imprévu géré » dans le rapport.Example: quick reconnection. A step fails because an “Session expired” popup covers it. Handler 1 — screen: the popup text; step: tap OK. The tap logs out and brings the login screen. Handler 2 — screen: the login screen; step: a call to the “Log in” scenario; resume: go back to the original screen. The engine taps OK, logs in again, goes back where it was, and replays the step: passed, with “interruption handled” in the report.

Garde-fous : jamais d’imprévu dans un gestionnaire ; au plus 3 tours par pas, une douzaine par exécution, un nombre maximum de déclenchements par gestionnaire ; tout est tracé dans le rapport (ce qui a été vu, ce qui a été fait, si ça a marché). Le réglage Imprévus (Paramètres → Exécution) permet de choisir : complet, gestionnaires et app disparue seulement, ou désactivé. En création, les dialogues système sont répondus pour l’agent, le rejeu de la proposition applique vos gestionnaires, et l’agent est invité à ne pas inclure dans le scénario une popup qu’il a dû fermer.Safeguards: never an interruption inside a handler; at most 3 rounds per step, a dozen per run, a maximum number of triggers per handler; everything is traced in the report (what was seen, what was done, whether it worked). The Interruptions setting (Settings → Execution) lets you choose: full, handlers and vanished app only, or off. In creation, system dialogs are answered for the agent, the proposal replay applies your handlers, and the agent is asked not to include a popup it had to close in the scenario.

Diagnostic : comprendre un échecDiagnostics: understanding a failure

  • Vidéo : chaque scénario est filmé, la vidéo n’est gardée que s’il échoue. Elle se lit dans le détail du pas, ouverte quelques secondes avant lui. Réglable (Paramètres → Exécution).Video: every scenario is filmed and the video is kept only if it fails. It plays in the step detail, opened a few seconds before it. Adjustable (Settings → Execution).
  • Journal de l’appareil : syslog iOS filtré sur le processus de l’app, logcat Android sur son package. Les lignes utiles autour de l’échec sont jointes au pas et à l’analyse IA.Device log: iOS syslog filtered on the app’s process, Android logcat on its package. The useful lines around the failure are attached to the step and to the AI analysis.
  • Signes de problème réseau détectés dans ce journal : hors ligne, délai dépassé, connexion refusée, certificat/TLS, réponses 5xx, accès refusé 401/403 — « ce n’est pas l’app, c’est le réseau ».Signs of network trouble found in that log: offline, timeout, connection refused, certificate/TLS, 5xx responses, 401/403 access denied — “it is not the app, it is the network”.
  • Comparaison visuelle avec la dernière réussite du même pas : les zones qui ont changé sont entourées, avec le pourcentage de l’écran qui diffère (la barre d’état est ignorée). Un écart quasi nul oriente vers un problème de timing ou de données, un écart massif vers un autre écran.Visual comparison with the last pass of the same step: changed areas are outlined, with the percentage of the screen that differs (the status bar is ignored). A near-zero gap points to timing or data, a huge one to another screen.

VitesseSpeed

  • Android et iOS sont pilotés en parallèle : la durée est celle de l’OS le plus lent, pas la somme.Android and iOS are driven in parallel: the duration is that of the slowest OS, not the sum.
  • Attentes sur condition : détection de changement d’écran en quelques requêtes légères, nouvel essai immédiat puis espacé, attente du clavier plutôt qu’un délai fixe.Condition-based waits: screen-change detection in a few light requests, immediate then spaced retries, waiting for the keyboard rather than a fixed delay.
  • Raccourci par lien profond : un écran de départ peut porter un lien (par OS). Il est essayé avant de relancer l’app et de rejouer un parcours ; s’il n’atterrit pas au bon endroit, le chemin sûr reprend.Deep-link shortcut: a start screen can carry a link (per OS). It is tried before relaunching the app and replaying a route; if it does not land in the right place, the safe path takes over.
  • Profil de durée : Progression liste les pas les plus lents et la part du temps passée en preuves plutôt qu’à agir ; l’outil MCP slowest_steps y ajoute des suggestions. Le niveau de preuves (tout, écrans clés, échecs) se règle.Duration profile: Progress lists the slowest steps and the share of time spent on evidence rather than acting; the MCP tool slowest_steps adds suggestions. The evidence level (all, key screens, failures) is adjustable.

CI/CD : lancer sans fenêtreCI/CD: run without a window

Un runner CI jetable n’a ni téléphone ni émulateur. Le principe : la CI déclenche, un poste dédié exécute. Le pipeline construit l’app, puis lance Cybermonkey --cli run sur une machine de test (agent Jenkins, runner GitHub ou GitLab auto-hébergé) où sont branchés les appareils. La commande installe le build, joue la campagne et écrit les rapports.A throwaway CI runner has no phone or emulator. The principle: the CI triggers, a dedicated machine executes. The pipeline builds the app, then runs Cybermonkey --cli run on a test machine (Jenkins agent, self-hosted GitHub or GitLab runner) where the devices are plugged in. The command installs the build, plays the campaign and writes the reports.

Cybermonkey --cli run --project "Atlas Mobile" --env recette \
  --android-app app-debug.apk --fresh --out reports --artifacts
  • Installation du build : .apk (Android), .app (simulateur iOS) ou .ipa (iPhone). --fresh désinstalle d’abord : départ sans aucune donnée.Build installation: .apk (Android), .app (iOS simulator) or .ipa (iPhone). --fresh uninstalls first: a start with no data at all.
  • Rapports : junit.xml (affichage natif dans Jenkins, GitHub, GitLab), html.html, json.json ou tout format d’export ; --artifacts ajoute captures et vidéos.Reports: junit.xml (shown natively by Jenkins, GitHub, GitLab), html.html, json.json or any export format; --artifacts adds screenshots and videos.
  • Mêmes réglages que l’application : projets, appareils associés, imprévus ; --env choisit l’environnement pour cette exécution seulement.Same settings as the app: projects, paired devices, interruptions; --env picks the environment for this run only.

Distinguer l’app est cassée (1) de la machine est cassée (2) évite qu’une alerte de régression se déclenche parce qu’un téléphone s’est débranché. Un téléphone ne faisant qu’un test à la fois, sérialisez les jobs côté pipeline (lock, concurrency, resource_group) ; préférez émulateurs et simulateurs aux téléphones physiques. Pas encore : serveur et file d’attente, création de scénarios en ligne de commande. Appareils distants (réseau, cloud) : voir plus bas. Exemples Jenkins, GitHub Actions et GitLab : docs/cli.md.Telling the app is broken (1) from the machine is broken (2) keeps a regression alert from firing because a phone got unplugged. A phone can only run one test at a time, so serialize jobs in the pipeline (lock, concurrency, resource_group); prefer emulators and simulators over physical phones. Not yet: a server and queue, creating scenarios from the command line. Remote devices (network, cloud): see below. Jenkins, GitHub Actions and GitLab examples: docs/cli.md (French).

Intégrations : Git, messagerie, outils de test, ticketsIntegrations: Git, chat, test tools, tickets
